# PARTIE 10 — Étapes 21 à 30 (SAV → Pricing/onboarding/growth)

## ÉTAPE 21 — SAV
**A/B/C** Objectif : le SAV est la **continuation du dossier**, jamais un dossier orphelin. Acteurs : secrétaire, technicien, dirigeant, client. Experts : responsable SAV, qualité, data.
**D** Recherche universelle → toiture, chantier, équipe, travaux, diagnostic, photos avant/après, facture, garantie, historique.
**E/F/G** *Client* : appelle, n'a rien à réexpliquer, reçoit un créneau et un suivi. *Secrétaire* : ticket en 3 taps (type, urgence eau ?, chantier lié). *Système* : calcule la garantie, propose la qualification, attribue, planifie, chaîne résolution→cause→clôture→satisfaction.
**H/I** Fiche ticket liée à la toiture ; mobile technicien : intervention SAV comme une mission. **J/K/L** `support_ticket{type,priorité,chantier,sous_garantie,cause,résolution,coût}`. Automatisations : ticket → tâche/RDV ; clôture → satisfaction ; cause récurrente → alerte qualité. IA V2 : classification proposée. **M/N** Notifications : fuite en cours = URGENT. **O/P/Q** Edge : hors garantie (devis), client de mauvaise foi (notes internes limitées et légalement prudentes), ticket sans chantier retrouvé. **R/S** KPI : retours/90 j, délai de résolution, top 5 causes, coût SAV/chantier. **W** Acceptation : le SAV retrouve tout le contexte sans ressaisie ; le coût remonte sur la marge du chantier d'origine. **X/Y/Z** MVP : tickets liés (V1) ; **Décision** : SAV = objet lié à la toiture/chantier. **RED** : ticket créé hors système → numéro unique + recherche ; **SIMPLIFY** 5 types ; **SIMULATE** 08:20 appel « fuite après travaux » → chantier retrouvé, garantie oui, créneau demain 9 h ; **VALIDATE** causes réelles.

## ÉTAPE 22 — ENTRETIEN (moteur de LTV)
**A/B/C** Objectif : transformer une vente ponctuelle en relation longue. Acteurs : commercial, technicien entretien, système, client. Experts : lifecycle marketing, Customer Success, technicien entretien.
**D** Toiture (âge, matériaux), dernier passage, anomalies surveillées, règles **configurables et validées métier**.
**E/F/G** *Client* : reçoit un rappel pertinent (« votre toiture a 2 ans de travaux ») et une proposition simple. *Employés* : visite planifiée automatiquement ; anomalies « surveillées » revues. *Système* : prochaine échéance calculée, rappel J-30, opportunité si anomalie, renouvellement de contrat. **Aucune recommandation technique arbitraire** : règles écrites par l'entreprise.
**H/I** Contrats/visites `[EXISTE partiel]` ; carnet de santé lisible client. **J/K/L** `maintenance_plan`, `service_visit`, `roof.timeline`. Automatisations : chantier clos → échéance ; visite faite → carnet mis à jour ; anomalie → opportunité. **M/N/O** Edge : client refuse le contrat, déménagement (transfert propriété), échéance à une saison chargée. **R/S** KPI : part CA récurrent, taux de renouvellement. **X/Y/Z** MVP : contrats + rappels `[EXISTE]` ; V1 carnet de santé ; V2 campagnes. **RED** : rappels perçus comme du spam → 1/an + valeur (état de la toiture) ; **SIMULATE** N+1 : rappel → visite → « aucune anomalie » → prochain rappel ; **VALIDATE** règles d'échéance avec un couvreur.

## ÉTAPE 23 — AVIS / PARRAINAGE
**A/B/C** Objectif : transformer la satisfaction en réputation et recommandations, **loyalement**. Acteurs : client, système, commercial. Experts : referral, SEO local/Google Business, privacy.
**D** Réception signée, paiement, satisfaction.
**E/F/G** *Client* : reçoit **une** question de satisfaction (2 taps) ; si satisfait → lien d'avis + code parrain ; **si insatisfait → ticket de résolution, jamais d'avis filtré**. *Système* : J+2 après clôture+paiement ; 1 relance max.
**H/I** Page publique mobile ; **J/K/L** `review_request`, `referral{code,referrer,lead,conversion,récompense}`. Automatisations : `satisfaction_ok` → avis + parrain ; `referral_converted` → récompense. **M/N/O** Edge : client mécontent (workflow SAV), avis négatif public (réponse guidée), parrain sans achat. **R/S** KPI : taux de demande→avis, note, leads parrainés, coût par lead parrain. **X/Y/Z** V1 ; **Décision** : question de satisfaction **neutre pour tous**, jamais de porte sélective. **RED** : soupçon de manipulation → texte identique pour tous. **SIMULATE** J+2 satisfaction 5/5 → lien Google → 1 avis. **VALIDATE** règles des plateformes.

## ÉTAPE 24 — RÉACTIVATION
**A/B/C** Objectif : réveiller les clients/devis dormants sans spam. Acteurs : commercial, marketing. **D** Ancien client, devis perdu/expiré, toiture ancienne, dernier passage, météo. **E/F/G** *Client* : message pertinent (entretien dû, tempête, nouvelle offre) ; *Système* : segments (toiture > 15 ans, devis refusé pour « report », clients silencieux 24 mois), règles d'exclusion (opt-out, SAV ouvert). **H/I** liste ciblée + campagne simple. **J/K/L** `segment`, `campaign_send`. **M/N/O** Edge : client désabonné, doublons de campagnes, tempête (message factuel, non alarmiste). **R/S** KPI : taux de réactivation, CA réactivé, plaintes. **X/Y/Z** V1 segments simples, V2 campagnes météo. **RED** : sur-sollicitation → plafond 1 message/client/trimestre. **VALIDATE** consentements.

## ÉTAPE 25 — DASHBOARDS / COCKPIT
**A/B/C** Objectif : « je sais ce qui nécessite mon attention ». Acteurs : dirigeant, managers. **D** Événements, seuils. **E/F/G** Liste d'exceptions cliquables `[EXISTE partiel]` (leads non traités, devis non relancés, chantier bloqué, impayés, SAV, entretiens dus, campagne dégradée) + « tout est sous contrôle ». **H/I** 6 chiffres max/écran, comparaison période. **J/K/L** vues matérialisées, seuils paramétrables. **X/Y/Z** MVP cockpit d'exceptions ; **Décision** : pas de dashboard décoratif. **RED** : trop d'alertes → priorité + regroupement. **VALIDATE** 3 dirigeants lisent le cockpit en < 30 s.

## ÉTAPE 26 — ANALYTICS
Événements (section 33) + événements **produit** (137) : temps de création lead, temps RDV, durée diagnostic, diagnostic→devis, devis→envoi, signature→planification, % diagnostics incomplets, échecs de synchro, usage mobile, automatisations déclenchées/corrigées. **North Star** : *nombre de dossiers menés jusqu'à l'encaissement complet avec une marge positive, par mois et par entreprise* (proxy de valeur créée), avec secondaires : délai lead→premier contact, % devis relancés, % missions avec journal complet, part de CA récurrent. **Définition écrite de chaque KPI** (numérateur, dénominateur, période, exclusions). **RED** : métrique de vanité (connexions) écartée. **VALIDATE** calcul sur données pilotes.

## ÉTAPE 27 — IA TRANSVERSE
Cadre unique (section 22) : gateway (plafonds, redaction PII, journal, timeouts, repli), **IA observable** (input, sortie, validée/refusée, correction, coût, latence — les corrections servent à améliorer), **fallback** : le métier continue sans IA. Cas par ordre : (1) résumé d'appel, (2) dictée→constat, (3) brouillon rapport, (4) brouillon devis (pas de prix inventé), (5) brouillon relance, (6) compte rendu chantier, (7) assistant dirigeant (requêtes prédéfinies, chiffres vérifiables). Évaluation : jeu de tests par tâche (100 cas réels annotés), seuil d'acceptation, suivi du taux de corrections. **RED** : prompt injection via texte client → contexte isolé, outils en lecture. **VALIDATE** H1 (dictée acceptée).

## ÉTAPE 28 — AUTOMATISATIONS TRANSVERSES
Moteur « quand / si / alors » (section 23) : catalogue **prédéfini et paramétrable** au MVP, éditeur en phrases en V2, pas de no-code complet. Observabilité : journal d'exécution, taux d'échec, simulation, idempotence, plafonds, profondeur max 3. **Fallbacks** : SMS échoué → e-mail ; webhook → retry ; Meta indisponible → file/CSV ; paiement retardé → réconciliation. **RED** : règles contradictoires → validation à l'enregistrement. **VALIDATE** 10 règles rejouées sur 100 dossiers.

## ÉTAPE 29 — BACK-OFFICE MAÎTRETOITURIER (Super Admin)
Deux niveaux : **Admin entreprise cliente** et **Super Admin plateforme** (organisations, abonnements, usage, support, intégrations, incidents, feature flags, coûts IA, stockage, audit, **impersonation** strictement tracée, limitée dans le temps, avec consentement du client). **Support mode** : le support voit identifiants d'événements, journaux, état de synchro, versions de l'app, erreurs récentes — sans données sensibles inutiles. **Health** : usage par entreprise, risque de churn (usage en baisse), configuration incomplète. **RED** : impersonation abusive → journal immuable + alerte. **VALIDATE** procédure de support écrite.

## ÉTAPE 30 — PRICING / ONBOARDING / GROWTH
**Pricing** (section 34 + 162/166) : socle entreprise + sièges bureau + sièges terrain très bas/gratuits + usage (SMS, IA, stockage). **Coût par entreprise (ordre de grandeur, à vérifier)** : base de données+app ≈ faible fixe mutualisé ; **photos** = poste dominant ; e-mail/SMS et IA à l'usage ; cartes/itinéraires à l'appel ; supervision/support mutualisés. **Photos à l'échelle** (hypothèse 40 photos/chantier × 30 chantiers/mois × 1,2 Mo compressée ≈ 1,4 Go/mois/entreprise) : 10 entreprises ≈ 15 Go/mois ; 100 ≈ 150 Go ; 1 000 ≈ 1,5 To ; 10 000 ≈ 15 To — d'où compression 1600 px, miniatures, originaux archivés à froid après N mois, quotas par plan. **Onboarding progressif** (144) : créer l'entreprise → inviter (facultatif) → importer/ajouter un client → diagnostic minimal → première mission ; réglages avancés plus tard ; **import assisté** (145) : détection de colonnes, mapping, doublons, aperçu, rollback `[partiel : CSV livré]`. **Growth/expansion** (167) : commencer CRM + diagnostic, ouvrir commercial → chantier → entretien → analytics **par valeur constatée**, jamais par dark pattern. **RED** : plan trop complexe → 3 plans lisibles. **VALIDATE** entretiens de prix avec 10 dirigeants.
